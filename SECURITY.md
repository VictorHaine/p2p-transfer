# Security Policy

## Supported Versions

Only the latest released version is supported for security fixes until the project publishes stable release branches.

## Reporting a Vulnerability

Do not open a public issue for suspected vulnerabilities.

Use GitHub private vulnerability reporting or a private maintainer contact for:

- cryptographic bypasses, PAKE confirmation failures, or signaling MITM paths
- file overwrite, path traversal, symlink, hardlink, or partial-file cleanup issues
- unauthenticated signaling state transitions
- denial-of-service vectors that bypass the documented rate limits or caps
- dependency, packaging, Docker, or CI supply-chain problems

Include:

- affected version or commit
- exact command sequence or packet/message sequence
- impact and whether file contents, file names, keys, or local files are exposed
- proof of concept if one exists

Expected response target: acknowledge within 72 hours, patch or publish mitigation guidance before public disclosure when the report is valid.

## Security Invariants

The project is expected to preserve these invariants:

- conforming clients must never send the signaling server the two secret words, PAKE output, plaintext file names, plaintext MIME types, file bytes, DataChannel plaintext, exact file count, exact manifest total bytes, exact encrypted-manifest JSON length, or declared per-file sizes; the server must reject unredacted public pair-request manifests from modified clients without forwarding or logging them, and it still receives routing metadata, bucketed public upper bounds for file count and total bytes, message timing/sizes, traffic volume, and authenticated SDP/ICE contents
- the signaling server must not relay arbitrary peer-controlled disconnect text or stateful internal teardown text; client `bye.reason` values and server cleanup reasons must be reduced to a fixed server-owned reason set before any `peer-left` forwarding
- production or non-loopback TURN REST deployments must require an explicit acknowledgement that the server cannot cryptographically verify receiver accept authenticity before minting short-lived relay credentials; operators must pair that acknowledgement with TURN-side allocation quotas, bandwidth caps, and abuse monitoring
- wire-incompatible changes must bump `PROTOCOL_VERSION` and the current conformance fixture together
- the server-visible rendezvous prefix must have enough namespace to resist cheap live-code enumeration and griefing; do not shrink it below eight decimal digits
- transfer code inputs must be capped before trim/lowercase normalization so CLI and browser callers cannot turn malformed local input into avoidable allocation pressure
- transfer code helpers must reject non-string runtime values before length, trim, lowercase, or regular-expression processing so exported parsing helpers cannot invoke hostile string-like methods
- retry/restoration paths must not re-acknowledge expired receiver rendezvous registrations
- clients must reject `registered` acknowledgements whose rendezvous prefix does not match the requested receive code
- client event listeners for ICE config, pair decisions, and WebRTC signaling must revalidate emitted signaling records before any field reads so public event emitters cannot bypass schema guards
- authenticated WebRTC ICE candidates must be converted to defensive own-data copies before both immediate native handling and queued delayed handling so candidate processing cannot observe mutated signal objects or invoke candidate accessors
- local WebRTC ICE candidate callbacks must snapshot native event and candidate data into defensive plain records before signal authentication and signaling send, and browser candidate serialization must locate `toJSON` through data descriptors on the candidate/prototype chain so malformed local event objects cannot invoke accessors or mutate the candidate payload between HMAC and transport
- browser WebRTC ICE candidate callbacks must copy the signal-authentication key, clear their handler, and wipe that callback-owned copy before session-key wipe; callback failures must close the peer connection without retaining live session key objects
- client public manifest redaction must walk manifest fields and file entries through own data descriptors so future local call-surface changes cannot invoke accessors or leak caller-owned ids, names, or MIME types
- client public manifest redaction must use bucketed file counts, bucketed total bytes, and synthetic per-file sizes that sum to the bucketed total, so the signaling server can validate a bounded manifest without seeing exact file count, exact manifest total bytes, or declared per-file sizes
- encrypted manifest wrappers must be padded before AEAD sealing so signaling frame sizes reveal only a coarse encrypted-manifest bucket instead of exact private filename, MIME, and manifest JSON length
- session ids in every signaling message schema must be restricted to the URL-safe nanoid alphabet, not arbitrary bounded or printable strings
- PAKE confirmation must complete before pair requests and WebRTC signaling advance
- PAKE confirmation and session key derivation must bind the protocol version, session id, and peer roles so future mixed-version or downgraded peers fail before pair request acceptance or WebRTC signaling
- clients must enforce a local authenticated WebRTC signaling replay guard before native `RTCPeerConnection` handling: one expected SDP transition per role, no opposite-role SDP, and no repeated ICE candidate payloads
- base64 encoding and decoding helpers must reject malformed or non-canonical runtime values before Buffer, atob, btoa, byte-length, iterator, or string conversion; decoding must have a global maximum input size, and low-level PAKE share and HMAC tag handling must reject wrong-sized base64 values before decoding so embedders and future call sites cannot turn malformed peer input into avoidable allocation pressure
- low-level PAKE and signal-auth helpers must validate role, session id, and code context bounds before key derivation or HMAC so future call sites cannot bypass signaling-schema limits
- PAKE share and encrypted manifest wrapper parsers must read wrapper fields through own data descriptors so missing wrapper tags cannot be supplied by Object prototype pollution
- PAKE state and session cleanup helpers must read cleanup fields through own data descriptors, require canonical PAKE state byte arrays before finish, and make cleanup best-effort so hostile accessors cannot run or prevent valid buffer wiping
- signaling frame serialization must reject symbol-keyed records, ignore inherited `toJSON` hooks, reject own accessors or own `toJSON` hooks, and re-parse the serialized frame through the protocol schema so outbound validation cannot be bypassed by prototype pollution, hostile objects, or locally constructed messages with unknown fields
- signaling frame serialization must reject non-finite numbers instead of silently rewriting them to `null`, because malformed protocol state should fail closed before it reaches the WebSocket
- exported signaling JSON parsers must reject non-string direct inputs before length, byte-length, JSON parsing, or string-like coercion
- signaling text-frame parsing must reject non-canonical binary frames before byte-length reads or UTF-8 decode so exported parsers cannot execute typed-array-subclass accessors
- sender claims of a receiver rendezvous must consume the strict one-shot pre-pair attempt budget before the receiver is moved into a paired session; any malformed PAKE payload or invalid sender flow before pair acceptance must expire the receiver code instead of allowing another online guess, and must not strand the receive flow
- pre-pair attempt helpers must reject malformed, unsafe, and over-budget runtime counters before decrementing or deciding receiver restoration
- invalid sender signaling before pair acceptance must restore or expire the receiver code immediately instead of stranding the receiver until session timeout
- raw PAKE/HKDF output buffers and WebCrypto input copies of keys, nonces, AAD, plaintext, or ciphertext must be wiped after deriving imported keys or running AEAD operations; retained session keys must be explicit copies
- exported hash helpers must read digest methods through data descriptors and require canonical 32-byte SHA-256 output before hex encoding so malformed hash-like objects cannot execute accessors or feed weak digest output into integrity checks
- WebCrypto AES keys must be imported with the minimum role-specific usages: manifest senders encrypt, manifest receivers decrypt, send keys encrypt, and receive keys decrypt
- exported AEAD helpers must read session key fields through own data descriptors and require non-destroyed `CryptoKey` fields before encryption, decryption, AAD construction, or wiped-key checks so malformed embedders cannot execute accessors or push bogus keys into WebCrypto
- exported HMAC authentication helpers must reject non-canonical or non-32-byte binary keys and copy them before dependency calls so malformed embedders cannot execute typed-array length accessors or accidentally authenticate with weak caller-provided keys
- CLI crypto dependency runtime attestation must verify the exact resolved entry file path and SHA-256 digest for the reviewed CPace, CPace-resolved noble curves, CPace-resolved noble hashes, and direct noble hashes files using bounded no-follow file reads with pre/post-read identity checks before importing the crypto runtime
- SDP and ICE signaling must be authenticated with the PAKE-derived signaling key
- schema allowed-key checks must reject non-enumerable and symbol properties so exported validators cannot accept hidden fields outside the JSON parser path
- WebRTC signal auth helpers must reject noncanonical signal shapes before computing HMAC tags so future call sites cannot accidentally leave extra SDP or ICE fields unauthenticated
- WebRTC signal auth helpers must reject accessor-backed signal records and read canonical SDP/ICE fields through own data descriptors before signing or verifying so exported auth paths cannot execute own or inherited getters
- WebRTC signal auth helpers must byte-cap SDP and ICE string fields before canonical JSON construction or HMAC so direct exported calls cannot bypass signaling frame byte limits with multi-byte strings
- exported CLI WebRTC helpers must reject malformed createPeer construction inputs, PeerConnection, DataChannel, signal, and backpressure-limit inputs before accessor reads, numeric coercion, native WebRTC calls, or timer setup; createPeer must snapshot ICE servers, signaling send, relay policy, and the signal-authentication key before asynchronous ICE callbacks
- relay policy helpers must read session, peer, message, and redacted-manifest fields through own data descriptors, walk manifest arrays by own element descriptors, and mutate phase flags only through own writable data descriptors so exported policy helpers cannot execute hostile accessors while making role/phase decisions or applying phase transitions
- server-visible redacted pair-request manifests must reject unknown manifest and file-entry fields at the relay policy layer, including symbol fields, so future call paths cannot smuggle plaintext metadata alongside encrypted placeholders
- session peer-id helpers must reject malformed runtime ids before selecting the opposite peer so exported policy helpers cannot silently route cleanup or relay decisions to the receiver side on invalid input
- authenticated ICE candidate relay must still be bounded per session peer; do not rely only on coarse connection rate limits for candidate spam
- authenticated WebRTC signaling failures must surface as security failures, not generic NAT, timeout, or disconnect failures
- encrypted payload authentication/decryption failures must surface as security failures, not generic transfer failures
- CLI and browser error classification and error rendering must read error messages through data descriptors and must not call `String(error)` or hostile `message` accessors while deciding retry, exit-code, or JSON error output
- browser top-level send and receive error logs must not persist selected local filenames, peer-supplied filenames, browser output names, or browser partial names; consent UI and actual output/download names are the only browser surfaces allowed to show those names
- CLI error output must redact quoted and unquoted absolute local filesystem paths, including POSIX paths, Windows drive-letter paths, Windows UNC or extended paths, and `file://` URLs, before human or JSON rendering, so platform filesystem exceptions cannot reintroduce path leakage after CLI-specific validation messages
- CLI entrypoints must set `process.exitCode` after printing output instead of calling `process.exit()` directly, so piped human or JSON output is not truncated before Node flushes stdout/stderr
- fixed-window hit recording must retain from the bounded tail instead of filtering arbitrary caller arrays so exported rate-limit helpers cannot become allocation vectors
- fixed-window rate-limit helpers must reject malformed runtime values before arithmetic, bound retained hit counts, and read timestamp arrays through own data descriptors so exported helpers cannot invoke hostile numeric coercion or array accessors
- server-side abuse buckets must derive keys from normalized IP literals only; socket remote addresses must reject empty, overlong, control-bearing, whitespace-bearing, hostname, or non-IP values before any trusted-proxy or rate-limit decision, and `X-Forwarded-For` must not be trusted unless `TRUSTED_PROXY_HOPS` is explicitly set and the socket peer matches `TRUSTED_PROXY_IPS`; when enabled, forwarded client IP parsing must use validated raw headers, reject malformed, duplicated, over-hop, control-bearing, hostname, untrusted-proxy, or accessor-backed header evidence, and fail closed to the socket address
- encrypted JSON sealers must preflight JSON depth, node count, accessors, symbol-keyed properties, cycles, and plaintext byte size, then serialize through descriptor-owned data only so low-level crypto helpers cannot become an allocation vector or execute inherited `toJSON`
- manifest validators, manifest comparison helpers, and control-message parsers must walk control fields, manifests, file arrays, and file metadata by own data descriptors, reject unknown manifest and file-entry fields, reject sparse or accessor-backed entries before touching peer metadata, and never read inherited fields through Object prototype pollution
- signaling schema predicates for manifest and ICE arrays must reject sparse or accessor-backed array entries before reporting a message as valid
- signaling schema predicates must byte-cap PAKE, SDP, and ICE string fields before accepting direct validator calls so embedders cannot bypass text-frame byte limits with multi-byte strings
- plain-record schema predicates must reject own string-keyed, symbol-keyed, or inherited accessor-backed records before field reads so exported validators cannot execute hostile getters, including through Object prototype pollution
- DataChannel control messages and bulk chunks must be encrypted with direction-specific AEAD keys
- bulk AEAD helpers must reject non-canonical binary values, non-binary values, and oversized plaintext or ciphertext payloads before byte-length reads or WebCrypto calls, even when called outside the chunk frame decoder
- chunk framing helpers must reject non-canonical binary values and non-binary runtime values before typed-array coercion or byte-length reads so exported helpers cannot invoke hostile array-like or typed-array-subclass getters or allocate from object-shaped input
- DataChannel binary ingress must reject DataView, typed-array subclasses, and other non-canonical views before reading `buffer`, `byteOffset`, or `byteLength`; peer-controlled frame normalization must only accept exact `ArrayBuffer`, exact `Uint8Array`, and exact Node `Buffer` values
- DataChannel abort notifications must not include local exception text; they should send a fixed generic reason and keep details local
- DataChannel transfer manifests must enforce file-count limits before allocating normalized file-entry arrays
- DataChannel control-message validators must not use stateful regular expressions for peer-controlled strings, because repeated validation must reject the same malformed abort reason every time
- exported control acknowledgement waiters must reject malformed acknowledgement types, ids, and timeout values before string-key construction, timer setup, or timeout-message interpolation, and must unref timers through descriptor lookup rather than optional accessor reads
- byte and rate formatters must reject non-finite, negative, and non-number runtime values before numeric coercion so exported progress display helpers cannot invoke hostile numeric conversion methods or print invalid units
- display text sanitization must cap raw strings before regex replacement so error/log handling cannot become an avoidable allocation vector
- display text sanitization must reject non-string runtime values before length, slice, replacement, or trim processing so exported output helpers cannot invoke hostile string-like methods
- CLI JSON output sanitization must sanitize object keys with per-record collision counters and stop traversing after explicit depth/node caps for cyclic, deeply nested, collision-heavy, or very wide structured values so defensive logging cannot become a terminal-spoofing, crash, CPU, or allocation vector
- server operational logs must not include signaling payloads, receiver codes, session ids, peer identifiers, peer IPs, arbitrary exception messages, raw configuration values, raw static-root paths, bind addresses, bind ports, or stack traces; startup configuration/static-root failures, startup/shutdown logs, and fatal server errors may report only fixed operational text plus descriptor-read process signal, sanitized configuration error names, or OS error code/syscall/class fields
- server-initiated WebSocket close frames and `peer-left` messages must map internal teardown reasons to a fixed close-text vocabulary, so peers cannot learn rate-limit, backpressure, invalid-attempt, unavailable-peer, timeout, or other stateful server cleanup reasons from the WebSocket close reason or signaling payload
- CLI JSON output sanitization must walk arrays and records through property descriptors, never getters or iterators, and must count primitive slots/properties against the traversal budget
- CLI JSON output sanitization must remove JSON stringify hooks, shadow inherited `toJSON` on sanitized arrays and records, truncate non-plain objects, and replace non-JSON primitive values so the final `JSON.stringify` cannot execute peer-controlled getters or `toJSON` code, silently convert non-finite numbers to `null`, or crash on BigInt/Symbol/function values
- incoming DataChannel setup must close any already accepted partial channels when setup fails on timeout, duplicate labels, or invalid channel parameters
- queued receiver DataChannel handlers must stop after transfer completion as well as failure, so late queued peer events cannot touch session keys, transfer state, or output files after final acknowledgements and teardown begin
- queued receiver DataChannel handlers must cap queued message count and queued byte length before entering the async transfer queue, and unsupported payload types must fail closed as over-limit queue input
- queued sender acknowledgement handlers and channel-close handlers must stop after transfer completion, so late queued peer acknowledgements or close events cannot touch session keys or flip a completed send into a failure during teardown
- incoming DataChannel setup must snapshot and validate the accepted event channel and channel object before reading labels, channel parameters, closing unexpected channels, or interpolating duplicate-label errors
- incoming DataChannel setup must also fail on terminal WebRTC peer-connection states while waiting, without replacing the shared connection-state handler
- WebRTC peer-connection waiters must evaluate the current connection state immediately after installing their state-change handler so already-terminal connections fail closed instead of waiting for timeout
- DataChannel open and backpressure waiters must check terminal channel states before success/low-buffer fast paths; open waiters must re-check for already-open channels after installing handlers, and close/backpressure waiters must re-check after installing handlers, so open/close races complete correctly or fail closed instead of waiting for timeout
- CLI timer helpers must locate optional timer methods through data descriptors without invoking hostile accessors so exported timer utilities cannot execute malformed timer-like objects
- CLI interrupt helpers must locate signal listener methods through data descriptors, roll back partial listener registration failures, and use the hardened timer helper for cleanup waits
- browser sender preflight must descriptor-validate selected file arrays and enforce file-count limits before hashing any selected files
- browser and CLI senders must prehash selected files and verify per-chunk plus final hashes while streaming, so same-size content changes cannot be sent under an already accepted manifest
- browser and CLI senders must honor encrypted receiver resume offsets on `ready` acknowledgements, require and verify a receiver-supplied SHA-256 over any nonzero resumed prefix before sending suffix bytes, send an encrypted `restart` control message and fall back to byte `0` when the prefix hash does not match the sender's source file, reject unaligned or oversized offsets, and still verify the full sender-side file hash before sending `file-end`; CLI senders must also rehash and per-chunk verify any skipped resume prefix before sending resumed suffix bytes
- browser and CLI senders must re-check authenticated sender failure after local resume-prefix hashing, asynchronous file reads, awaited control/bulk sealing, and DataChannel backpressure waits, so a remote abort or channel close/error cannot be followed by another encrypted chunk, restart, or terminal acknowledgement
- browser sender preflight and transfer must hash/send deterministic `File.slice()` byte ranges, not browser stream chunk boundaries; streamed browser receive/publish data must still pass through canonical binary normalization before byte-length, subarray, fill, hashing, encryption, writing, or publish verification
- browser sender preflight must hash selected files sequentially rather than opening every file stream concurrently, so worst-case valid sessions cannot self-inflict browser resource exhaustion before the accept gate
- browser sender preflight must complete before sending the pair request, so large valid files cannot make the receiver accept, open WebRTC, and then time out while the sender is still hashing
- CLI sender preflight and send-time file stream chunks must reject non-canonical runtime chunks before byte-length, hashing, AEAD, framing, Buffer conversion, or cleanup so exported send helpers and monkeypatched file handles cannot invoke coercion or accessor gadgets
- CLI sender manifest builders must descriptor-validate selected file path arrays and reject empty, oversized, or control/format-character paths before path resolution or stat calls, so exported helpers cannot invoke hostile iterators, accessors, path-like coercion, or avoidable path-parser allocation
- CLI sender path preflight errors must not echo raw local send paths or canonical output directories to human or JSON output
- CLI and release helpers that consume sensitive environment values must read them through own data descriptors and clear them through descriptor-aware `Reflect.deleteProperty` checks, not unchecked `delete process.env[...]`, so non-configurable or otherwise uncleared local secret carriers fail closed instead of silently remaining available to later code
- CLI sender transfer boundary must descriptor-validate and bound send file arrays, entries, handles, read/stream methods, canonical hashes, and chunk hashes before constructing the immutable send plan; read/stream method lookup must use a bounded prototype walk, so exported helpers cannot invoke hostile accessors, clone oversized hash arrays, accept malformed integrity state, or mutate file I/O methods after validation
- browser folder receive publish must release source readers even when target writable creation fails, so failed folder publishes cannot retain source file locks or resources in long-lived browser sessions
- CLI filesystem path validators must reject overlong UTF-8 paths with early-exit byte counting instead of allocating full encoded copies before rejection
- CLI sender file cleanup must walk file arrays and handles through own data descriptors and settle every close attempt so cleanup cannot invoke hostile accessors or mask the original transfer/setup failure
- CLI receiver output-directory and reservation helpers must reject non-string, empty, oversized, or control/format-character paths before path resolution, mkdir, lstat, open, or path joining so exported helpers cannot invoke hostile path-like coercion or silently write into the process cwd; reservations must carry the output directory identity through partial creation and final publish so a replaced output-directory pathname cannot silently redirect received files
- CLI received files must never silently overwrite existing paths; browser folder receives must use high-entropy tokenized names and the File System Access caveats below because browsers do not expose CLI-style exclusive create, stable file identity, or atomic publish primitives
- CLI output publish copy fallbacks must carry forward the identity of the final file handle that was actually written and re-check the final path against that identity before returning, so a path swap after exclusive open cannot become the trusted published identity
- safe filename helpers must extract leaf names with a bounded reverse scan rather than allocating arrays from untrusted path-like strings
- safe filename helpers must reject non-string runtime values and over-budget collision indexes before leaf, reserved-name, collision, or UTF-8 byte processing so exported helpers cannot invoke hostile string-like methods or emit names outside the byte budget
- safe filename helpers must count UTF-8 bytes without full-buffer encoding so long accepted runtime strings cannot become allocation vectors
- exported basename helpers must extract leaves with a bounded reverse scan rather than splitting arbitrary path-like strings into arrays
- exported basename helpers must reject non-string runtime values before length, character, or slice processing so exported path display helpers cannot invoke hostile path-like methods
- CLI receive publish, copy fallback, and disk verification paths must carry the accepted file size through every same-identity check so a partial file cannot grow after hash verification and be copied or hashed beyond the accepted manifest
- CLI filesystem error classifiers must inspect `code` through own data descriptors and must not coerce arbitrary `code` values, because missing-path, collision, and copy-fallback decisions are security-sensitive
- accepted manifest filenames must already be portable output-safe; receiving code may still sanitize defensively, but validation must reject names that would be silently rewritten before publish
- exported CLI publish helpers must reject malformed publish paths, expected partial identities, and expected sizes before filesystem calls, identity comparisons, cleanup, or copy-loop arithmetic
- partial-file cleanup must not delete pathnames that were replaced after reservation
- CLI receive, reservation, and publish cleanup must quarantine same-directory verified paths before removal, recheck the quarantined path identity, and fail cleanup rather than deleting when identity changes between the original pathname check and deletion
- CLI receive cleanup failures after an existing transfer failure must preserve the root transfer error and may only emit a generic cleanup warning without output paths, partial paths, file names, platform error text, byte counts, or transfer metadata
- CLI resumable receive must be explicit, use no-follow same-directory private partials, truncate existing partials to chunk boundaries before advertising an encrypted `ready.offset`, hash existing partial bytes into the final verifier, reset to byte `0` on authenticated sender `restart`, and still require the sender's full-file SHA-256 before publishing
- CLI receive partial file names must be opaque `ff-<token>.part` or HMAC-derived `ff-resume-<digest>.part` entries and must not embed peer-supplied final file names; `recv --opaque-output-names` must publish final CLI receive paths as `ff-<token>` names or, with resume, stable per-output-directory HMAC-derived opaque names instead of peer-supplied basenames; resumable partial and opaque final names must be keyed by a per-output-directory random secret instead of an unsalted filename digest; resumable partial files must reject multiple hard links and non-private POSIX mode bits before hashing, truncation, restart truncation, or publish; partial and resume-secret creation must use exclusive no-follow creation flags; the resume secret file must be private, fixed-size, and opened with no-follow flags; newly created resume secrets must be verified as private, fixed-size, and single-link before keying resumable names; the resume secret file must reject multiple hard links before keying resumable names, and invalid or non-private resume secrets must fail closed; Windows CLI `recv --resume` must fail closed until equivalent ACL privacy checks are implemented
- browser folder receives must only create File System Access entries from base names and candidate names that contain a collision-resistant reservation token, stream into tokenized `.part` entries, and publish only after hash verification because File System Access does not provide the same exclusive create/atomic publish primitive as the CLI filesystem path
- browser receive must expose an explicit opaque-names mode for sensitive receives; when selected, final browser output names must publish as opaque `ff-<token>` names and resumed folder publishes must use stable opaque names derived from the browser-held resume identifier instead of peer-supplied basenames
- browser Blob download fallback must create generic `application/octet-stream` blobs so opaque download names are not silently given content-specific extensions by browser download heuristics
- browser receive resume must be explicit, exposed only for single-file manifests until privacy-preserving completed-file tracking exists, and limited to same-browser saved opaque tokenized `.part` records for the accepted manifest; resumed partials must be hashed, truncated to a valid chunk boundary or declared size, advertised only through encrypted `ready.offset` plus `ready.prefixSha256`, reset to byte `0` on authenticated sender `restart`, and still pass final sender SHA-256 plus browser publish verification before becoming visible as the final tokenized file
- browser receive must expose an explicit folder-only mode for sensitive receives; when selected, it must verify File System Access availability before registering a receive code and must remove the memory-backed Blob download fallback from the accept path
- browser receive resume registry keys must be HMAC identifiers over canonical manifest identity using a non-extractable browser-held HMAC-SHA-256 lookup key with 256-bit key material, not plaintext manifest, unsalted digest identifiers, file name, MIME, size, or count JSON; missing or invalid persisted browser resume lookup keys must clear the resume registry before a fresh persisted key is used, and unavailable browser resume lookup key storage must clear the registry and disable resume persistence for that attempt instead of writing records keyed by ephemeral in-memory key material
- browser receive must not create or load browser resume HMAC key material for ordinary folder receives; browser resume lookup keys may only be loaded after the user explicitly selects `Resume in folder`
- browser receive must expose a user-visible clear action that snapshots registry-known opaque partial names, offers to remove matching `ff-*.part` entries from a freshly selected folder when File System Access is available, removes origin-stored browser resume registry records, resets the in-memory resume lookup key, and deletes the IndexedDB resume lookup key store; it must not claim to enumerate or delete stale partials from folders the user did not freshly select
- browser receive local filesystem, hash, and publish work must not trip the peer-data idle watchdog for an otherwise healthy transfer; channel close/error handlers remain authoritative for peer failure while local-only work is active
- browser and CLI receive local filesystem, hash, decrypt, and publish work must re-check transfer failure before mutating transfer state, publishing final folder files, marking files done, or sending final acknowledgements; final file acknowledgements must be sealed before final publish/download and sent synchronously after the final stop check, and browser folder cleanup must remove any published final file if final acknowledgement fails, so a channel close/error during local-only folder work cannot turn a failed receive into a visible folder success; Blob fallback downloads cannot be recalled after the browser accepts the synthetic click, so sensitive browser receives must use Folder only
- cancelling the browser folder picker must keep the accept gate pending and must not send an authenticated `pair-reject`; only the explicit Decline action should reject a pending browser receive
- browser receive resume registry values must not persist plaintext file names, MIME types, or sizes; only opaque tokenized partial file names and bounded timestamps may be kept between attempts
- browser receive resume registry reads must scrub invalid, noncanonical, expired, or legacy metadata-bearing entries, clear stale storage before writing sanitized replacements, and browser startup must trigger that scrub so old persisted file names, MIME types, or sizes are removed without waiting for the next successful resume write
- browser folder receive publish must carry the accepted file size through partial copy and final verification so a changed partial snapshot cannot be copied before the receive path fails
- browser output name helpers must reject non-string names, non-string random tokens, and invalid collision indexes before regex, template-string, UTF-8, or path-splitting work so exported helpers cannot invoke hostile coercion
- browser output name helpers must count UTF-8 bytes without full-buffer encoding so direct helper calls with overlong names cannot become allocation vectors
- browser folder candidate-name validation must reject malformed base names and malformed candidate callbacks before invoking callback-controlled name generation or touching browser directory handles, and must reject overlong UTF-8 names with early-exit byte counting instead of allocating full encoded copies before rejection
- browser filesystem not-found classifiers must read DOMException names through the native prototype getter so hostile exception subclasses cannot forge absence or execute `name` accessors
- production browser deployments must restrict `ALLOWED_ORIGINS` and use `wss://`
- production browser deployments that use browser resume should run on a dedicated origin because origin-sharing scripts can inspect opaque resume registry entries and ask the browser-held lookup key to test guessed manifest identities
- production-mode checks must parse `NODE_ENV` fail-closed; whitespace, case variants, or unsupported values must not silently disable production origin, TURN, or CSP behavior

- production and non-loopback signaling deployments must explicitly declare `SIGNALING_TOPOLOGY=single-instance` or `SIGNALING_TOPOLOGY=sticky-sessions` because rendezvous state is in memory and random multi-replica routing breaks pairing

- production browser deployments must not allow arbitrary browser `wss:` destinations unless `BROWSER_ALLOW_ANY_WSS=true` is a deliberate deployment choice
- production browser deployments must not allow browser loopback `ws://` destinations unless `BROWSER_ALLOW_LOOPBACK_WS=true` is a deliberate private deployment choice
- browser security headers must keep no-referrer, HSTS, frame denial, MIME sniffing denial, COOP, COEP, CORP, Origin-Agent-Cluster, and a locked-down Permissions-Policy so the static app stays isolated from ambient browser embedding and cross-origin side channels

- server environment JSON and list inputs must be byte-capped before trim, split, JSON parse, or credential use so deployment mistakes cannot become avoidable startup allocation or per-request TURN HMAC pressure
- scalar server environment values must be byte-capped before trim, regex, numeric conversion, path resolution, or credential checks so oversized deployment input cannot reach parser or filesystem helpers before rejection
- `ALLOWED_ORIGINS` parsing must reject empty comma entries, leading/trailing entry whitespace, and over-cap origin counts while scanning, before normalization or URL parsing, so malformed allowlists cannot silently widen or narrow deployment policy
- `TURN_URLS` parsing must reject empty or over-cap JSON arrays before element validation, credential scans, or URL parsing so malformed relay configuration cannot force avoidable full-list work before rejection
- server configuration must reject non-string environment values before trim, split, JSON parse, URL parse, or byte-length checks so embedders cannot trigger coercion hooks or uncontrolled parser errors
- server configuration must read environment values through own data descriptors before validation so custom env objects cannot invoke getters while parsing policy or secrets

- the default static web root must resolve relative to the shipped server module, not the caller's current working directory, so global/package-installed `ff-server` serves the bundled web UI without requiring `WEB_ROOT`
- server configuration must reject `PORT=0` so deployments cannot accidentally bind an unadvertised ephemeral port
- server configuration must not support wildcard origin bypass flags; origin policy exceptions must be explicit and typed
- origin policy helpers must reject non-string runtime origins and descriptor-validate allowlists before loopback URL parsing or CORS reflection so exported helpers cannot invoke coercion or accessor-backed allowlist entries
